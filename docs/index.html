13 / Lessons Lessons (from the /address pass) 5
  • An "every-handler smoke test" is cheap insurance. /review-2 caught one column-mismatch bug (get_open_hypotheses); the regression test added during C3 exposed three more. Most of the agent's read surface would have crashed sqlite3 on first invocation. test_every_agent_tool_handler_executes_against_fresh_db is now a permanent guard against this class of bug.
  • The autocommit→atomic bug masked a worse second bug. Wrapping publish_post_atomic in a transaction required initializing consumed = None before the try block — without that defensive binding, the post-validation except Exception would UnboundLocalError on consumed.token_id.
  • C5 (IWH gate not wired) is the most consequential single fix. The entire epistemic discipline that Phase 5.5 exists to enforce was dead code in production — the model could call save_draft_post unconditionally and the test suite passed because tests called the orchestrator directly. Lesson: integration tests must exercise the production path end-to-end (dispatch_tool_call → handler), not just call the gate function in isolation.
  • Memory observation 7893 paid off across phases. A 2026-05-21 note flagged "Failing Tests Insert Second post_classifications Row to Simulate Reclassification — Must Use UPDATE Instead." When W12's UNIQUE migration broke two test_views.py tests, the memory entry explained exactly what to do.
  • AppTest smoke is necessary but not sufficient for interactive bugs. The publish-modal busy-loop (C4) passed AppTest before the fix because the modal isn't open during cold boot. Interactive behavior requires interactive testing (manual or Playwright); AppTest is an import-and-render gate only.

04 / LessonsWhat this phase taught
  • vcr.py + subprocess transport is a clean seam, but only if the cassette format is portable. The custom loader patches subprocess.run but the YAML it consumes is vcr.py-compatible — so a future transport migration to native requests (e.g. if xurl is dropped) plays back the same files without rewriting. Documented in docs/X_API_FIXTURES.md §1 as the rationale for the chosen path vs the rejected "rewrite to requests + manual OAuth signing" alternative.
  • The token-consumed matrix is the load-bearing correctness surface. 429 leaves the token UN-consumed (no X-side state change); 403 + 5xx + timeout all CONSUME the token (X considered it real, or X may have, and a retry would risk a duplicate post). Encoded in four separate except branches in publish_post_atomic; each branch has its own audit-log event_type so post-hoc forensics can distinguish failure modes without re-parsing error messages.
  • Manual fallback is load-bearing, not legacy. §29.1 promises manual workflows are inviolable as Settings-selectable fallbacks forever. The test_manual_fallback_round_trip_no_api_call test uses assert_no_x_api_calls to prove no xurl subprocess fires when publish_via_api_enabled=FALSE — if a future change breaks that, the test fails loudly. The Settings UI banner ("MANUAL-CLIPBOARD MODE · X API WRITES DISABLED") makes the state visible so Daniel can't accidentally believe API mode is active when it isn't.
  • Timeout is the only failure mode that publishes a "publish_method='unknown'" row. 429 / 403 / 5xx all set publish_method='failed' because they're definitive negative outcomes. Timeout is genuinely ambiguous — X may have processed the request — so the row needs to surface to the crash-recovery scan. The existing detect_orphans predicate (publish_method != 'failed' AND x_post_id IS NULL) already picks up unknown-method rows; the new reconcile_orphans_via_x_api auto-matches them by text hash and the manual-reconcile UI handles the rest.
  • POST + body in xurl argv = --request POST --data <json> <endpoint>. The Phase 7 request() helper was already shaped for this — POST is a first-class method argument and body_json serializes to --data. Phase 8's publish_post_to_x_via_api is a thin wrapper; no parallel argv-builder needed. Confirmed by the cassette-recorded argv: [xurl, --request, POST, --data, '{"text":"...","reply":{"in_reply_to_tweet_id":"..."}}', /2/tweets].
  • X API reply shape is nested, not flat. {"text": "...", "reply": {"in_reply_to_tweet_id": "..."}} — not in_reply_to_tweet_id at top level. publish_post_to_x_via_api builds the nested object only when an in_reply_to_x_post_id is passed; the resolver pulls the target's x_post_id from posts.in_reply_to_post_id → target posts row's x_post_id, not from the in-DB posts.id.
